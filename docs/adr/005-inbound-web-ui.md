# ADR-005 网页型 agent 通过入站中继访问

## 状态

已接受。

## 背景

DeepSeek Harness 通过网页界面和用户交互。网页服务运行在沙箱内。用户的浏览器运行在宿主机上。

沙箱只接入 Docker 的 internal 网络。实测证明，只接入 internal 网络的容器无法把端口映射到宿主机，见 [security.md](../security.md#6-验证记录) 的 V-14。

## 决策

### 入站链路

```
宿主机浏览器 ──► 127.0.0.1:<端口> ──► 入站中继容器 ──(internal 网络)──► 沙箱内的网页服务
```

- 入站中继容器同时接入 internal 网络和普通网络。
- 入站中继容器只把端口映射到宿主机的 `127.0.0.1`。
- 入站中继容器只转发到本沙箱网页服务的端口，不持有密钥。
- 每个使用网页界面的沙箱使用独立的入站中继和宿主机端口。

### 打开网页界面

- DeepSeek Harness 启动时输出带令牌的网址。
- Airlock 从启动输出中提取令牌，并校验令牌的格式。启动输出来自沙箱，按不可信数据处理。
- Airlock 用 `127.0.0.1` 和入站中继的端口拼接网址，再用浏览器打开。用户不需要复制令牌。
- DeepSeek Harness 启动时用 `--trusted-host` 参数信任这个地址。来源：[dsh 命令行文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md)。

## 备选方案

| 方案 | 不选的原因 |
|---|---|
| 沙箱直接映射端口 | 只接入 internal 网络时无法映射，见 V-14。 |
| 沙箱接入普通网络 | agent 可以绕过闸门直接出网。违反安全目标 G-3。 |
| 出网中继同时负责入站 | 出网和入站的转发目标不同。分开后，每个中继只有一个转发目标，更容易检查。 |
| 只使用 DeepSeek Harness 的命令行模式 | 命令行模式只能执行一次性任务，不能持续对话。 |

## 后果

- 好处：网页界面只能从本机访问。本机网页没有令牌，无法操作网页界面，见 V-15 和 V-16。
- 坏处：每个网页型沙箱多运行一个容器。
- 入站中继的启动和端口分配由 `architecture.md` 设计。
