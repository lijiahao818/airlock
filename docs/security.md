# 安全设计

本文档说明 Airlock 的威胁模型、防护措施和已知限制。术语见 [product.md](product.md#2-术语)。

## 1. 安全目标

| 编号 | 目标 |
|---|---|
| G-1 | 真实密钥不进入沙箱。 |
| G-2 | 真实密钥只发往预设的模型接口。 |
| G-3 | 沙箱的出网请求只能经过闸门。 |
| G-4 | agent 的文件改动经过用户确认后，才写入项目文件夹。 |
| G-5 | 放行决定只来自确定性规则或用户点击。 |
| G-6 | 用户误允许一个主机时，真实密钥仍然安全。 |

## 2. 信任边界

```
┌──────────────────── Windows 宿主机（可信）────────────────────┐
│  系统钥匙串    闸门进程    控制台    项目文件夹                 │
│                  ▲                                            │
│ ┌────────────────┼───── Docker Desktop 虚拟机 ──────────────┐ │
│ │            中继容器（半可信，不持有密钥）                    │ │
│ │                ▲                                          │ │
│ │ ┌──────────────┴─── 沙箱（不可信）──────────────────────┐ │ │
│ │ │  agent、占位符、暂存区                                 │ │ │
│ │ └───────────────────────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
```

- 宿主机可信。系统钥匙串、闸门进程和控制台运行在宿主机上。
- 沙箱不可信。来自沙箱的一切数据都按不可信数据处理。
- 中继容器只转发数据，不持有密钥，也不做放行决定。图中只画出了出网中继。入站中继只把宿主机 `127.0.0.1` 上的请求转发给沙箱的网页服务，见 [ADR-005](adr/005-inbound-web-ui.md)。
- 沙箱和宿主机之间隔着 Docker Desktop 的虚拟机。
- 暂存区位于宿主机，挂载进沙箱。agent 可以任意修改暂存区，所以暂存区的内容不可信。

## 3. 需要保护的资产

| 资产 | 位置 |
|---|---|
| 模型密钥 | 系统钥匙串、闸门进程内存。 |
| 项目文件夹 | 宿主机。 |
| 用户的其他文件 | 宿主机。 |
| 用户的提示词和代码 | 沙箱、模型请求的内容。 |
| 审计记录 | 宿主机。 |

## 4. 攻击者

| 编号 | 攻击者 | 能力 |
|---|---|---|
| A-1 | 被注入的 agent | 在沙箱内以普通用户身份执行任意命令。读写沙箱内的全部文件。 |
| A-2 | 恶意项目文件 | 在 README、`AGENTS.md`、skill 等文件中放入注入指令。 |
| A-3 | 本机网页 | 用户浏览器中的恶意网页向 `127.0.0.1` 发送请求。 |
| A-4 | 另一个沙箱 | 同一台电脑上的另一个被注入的 agent。 |
| A-5 | 恶意模型输出 | 安全副驾收到的模型输出不符合格式或内容有误导。 |

宿主机上已经运行的恶意程序不在防护范围内。

## 5. 威胁与防护措施

| 编号 | 威胁 | 攻击者 | 防护措施 | 对应目标 |
|---|---|---|---|---|
| T-1 | agent 读取环境变量或文件，取得真实密钥。 | A-1 | 沙箱中只有占位符。真实密钥只存于系统钥匙串和闸门进程内存。 | G-1 |
| T-2 | agent 把密钥发往攻击者的网站。 | A-1 | 闸门只在固定的模型接口路由上替换占位符。发往其他网站的请求只带占位符。 | G-2、G-6 |
| T-3 | agent 绕过闸门直接出网。 | A-1 | 沙箱只接入 Docker 的 internal 网络。internal 网络没有通往外部的路由。 | G-3 |
| T-4 | agent 通过 DNS 查询外带数据。 | A-1 | internal 网络不解析外部域名。 | G-3 |
| T-5 | agent 访问档位以外的网站。 | A-1 | 闸门暂扣请求，等用户决定。 | G-3、G-5 |
| T-6 | agent 在项目里留下后门文件。例如修改 Git hooks。 | A-1、A-2 | 改动先写入暂存区。出舱审查把高风险改动标为红色。用户确认后才写入项目。 | G-4 |
| T-7 | 项目里的密钥文件进入沙箱。 | A-2 | 进舱检查不把 `.env` 文件和私钥文件放进沙箱。 | G-1 |
| T-8 | agent 读取宿主机的其他文件。 | A-1 | 沙箱只能看到暂存区。不挂载宿主机 home 目录。 | G-4 |
| T-9 | agent 在沙箱内提权。 | A-1 | 以非 root 用户运行。删除全部 Linux 能力。禁止提升权限。根文件系统只读。 | G-1、G-3 |
| T-10 | agent 控制 Docker，创建不受限的容器。 | A-1 | 不挂载 Docker socket。不使用 `--privileged`。 | G-3 |
| T-11 | 本机网页借用闸门发送带真实密钥的请求。 | A-3 | 闸门只监听 `127.0.0.1`。闸门检查 Host 头。闸门只接受本次运行签发的占位符。 | G-2 |
| T-12 | 本机网页操作控制台，放行请求。 | A-3 | 控制台只监听 `127.0.0.1`。每个请求都要带启动时生成的随机令牌。 | G-5 |
| T-13 | 一个沙箱冒用另一个沙箱的身份。 | A-4 | 闸门按沙箱区分请求来源。每个沙箱使用自己的占位符。 | G-2、G-5 |
| T-14 | 注入指令诱导安全副驾建议放行。 | A-1、A-5 | 安全副驾只做解释，不做放行决定。安全副驾只收到事件元数据，不收到请求内容。 | G-5 |
| T-15 | 安全副驾把用户数据发给模型供应商。 | 无，属于设计风险 | 安全副驾只发送主机、端口、方法、路径、命中的规则和 agent 名称。 | — |
| T-16 | 日志或报错信息泄露密钥或提示词。 | A-1 | 闸门不记录请求体、请求头和查询参数。真实密钥不写入任何文件。 | G-1 |
| T-17 | agent 在暂存区放入符号链接或特殊路径，让"应用到项目"写到项目文件夹以外。 | A-1 | 出舱审查只应用项目文件夹内的普通文件。出舱审查拒绝符号链接和指向项目外的路径。 | G-4 |
| T-18 | 本机网页操作沙箱内 DeepSeek Harness 的网页界面，向 agent 下达指令。 | A-3 | 入站中继只映射到宿主机的 `127.0.0.1`。DeepSeek Harness 的网页界面要求启动令牌，并把令牌换成绑定 Host 的 cookie。 | G-5 |
| T-19 | agent 伪造网页界面的启动输出，让 Airlock 打开恶意网址。 | A-1 | Airlock 只从启动输出中提取令牌，并校验令牌的格式。网址由 Airlock 用固定的主机和端口拼接。 | G-5 |
| T-20 | agent 从包管理源安装恶意包，恶意包的安装脚本在沙箱内运行。 | A-1、A-2 | 安装脚本和 agent 受到同样的隔离和出网限制，拿不到真实密钥。安装脚本对项目文件的改动要经过出舱审查。 | G-1、G-4 |
| T-21 | agent 攻击 Docker Desktop 虚拟机网关上开放的服务。 | A-1 | agent 以非 root 用户运行，没有任何 Linux 能力，只能发起普通的 TCP 连接，不能伪造数据包。这些服务属于 Docker Desktop 虚拟机，不通往公网，也不在 Windows 宿主机上。保持 Docker Desktop 为最新版本，修补这些服务的漏洞。剩余风险见第 7 节。 | G-3 |

## 6. 验证记录

团队在一台 Windows 11 家庭版电脑上验证了沙箱的出网和入站控制。验证环境为 Docker Desktop 29.5.3、Claude Code 2.1.309、codex-cli 0.164.0、DeepSeek Harness 0.2.1-rc.2。测试使用的密钥都以 `fake-` 开头。

| 编号 | 测试内容 | 结果 | 对应威胁 |
|---|---|---|---|
| V-1 | 沙箱直接访问公网 IP。 | 失败：网络不可达。 | T-3 |
| V-2 | 沙箱解析外部域名。 | 失败：DNS 返回 SERVFAIL。 | T-4 |
| V-3 | 沙箱直接访问宿主机地址。 | 失败：网络不可达。 | T-3 |
| V-4 | 沙箱通过中继访问闸门。 | 成功。闸门收到占位符。 | T-1、T-2 |
| V-5 | 沙箱通过闸门访问白名单主机。 | 成功：返回 200。 | T-5 |
| V-6 | 沙箱通过闸门访问白名单以外的主机或 IP。 | 闸门拒绝。 | T-5 |
| V-7 | 沙箱不使用代理直接访问外部主机。 | 失败。 | T-3 |
| V-8 | 沙箱写入根文件系统。 | 失败：只读文件系统。 | T-9 |
| V-9 | 沙箱内使用 `su` 提权。 | 失败。有效能力集为 0。 | T-9 |
| V-10 | 沙箱查看宿主机 C 盘和 Docker socket。 | 两者都不存在。 | T-8、T-10 |
| V-11 | Claude Code 使用闸门地址和占位符。 | 模型请求发往闸门，请求头中只有占位符。 | T-1、T-2 |
| V-12 | Codex 使用闸门地址和占位符。 | 只设置 `OPENAI_BASE_URL` 时，Codex 仍向 `api.openai.com` 发请求，闸门拒绝了这些请求。改用配置文件中的自定义供应商后，模型请求发往闸门。 | T-1、T-3 |
| V-13 | DeepSeek Harness 使用闸门地址和占位符。分别测试命令行模式和网页界面。 | 两种模式的模型请求都发往闸门，请求头中只有占位符。没有其他出网请求。 | T-1、T-2 |
| V-14 | 只接入 internal 网络的沙箱直接映射端口到宿主机。 | 失败：宿主机连接被拒绝。 | T-18 |
| V-15 | 宿主机通过入站中继访问 DeepSeek Harness 的网页界面。 | 不带令牌时返回 401。带令牌时返回 cookie，页面可以正常使用。 | T-18 |
| V-16 | 携带有效 cookie，但把 Host 改为其他域名。 | 返回 401。 | T-18 |
| V-17 | 用宿主机的局域网 IP 访问入站中继。 | 失败：无法连接。 | T-18 |

## 7. 已知限制

- 沙箱之间共享 Docker Desktop 虚拟机的 Linux 内核。内核漏洞可以突破沙箱之间的隔离。
- 沙箱可以访问 Docker Desktop 虚拟机网关上开放的端口。验证时发现 111 和 59631 两个端口开放。这些服务有漏洞时，agent 可以借它们攻击 Docker Desktop 虚拟机。
- 闸门不解密 HTTPS。闸门对白名单内主机的请求内容不做检查。
- 只有支持自定义接口地址的 agent 才能使用占位符机制。
- Airlock 不管理 `git push` 等非模型接口的凭据。
- agent 可以把沙箱内的数据发往安全档位自动放行的主机。用户允许一个主机后，agent 在本次运行内可以持续向该主机发送数据。这些数据不包括真实密钥。
- 标准档位默认放行常用包管理源。理由有两条：沙箱中没有包的发布凭据，agent 无法上传包；agent 发往包管理源的数据存于包管理源，攻击者难以读到。攻击者仍可以借公开的下载计数等通道取得少量数据。恶意包的风险见 T-20。
- agent 可以通过闸门调用模型接口，消耗用户的模型额度。闸门保护密钥本身，不限制调用量。
- Airlock 依赖 Docker Desktop。Docker Desktop 自身的漏洞不在防护范围内。
- 宿主机上已经运行的恶意程序可以读取系统钥匙串。
- 沙箱的 `/tmp` 允许执行文件。DeepSeek Harness 把原生模块复制到 `/tmp` 后再加载。
- 团队没有验证 DeepSeek Harness 网页界面对 Origin 的检查。
